# The pipeline

Two generic engines over three ports, and the invariants that make them correct: build once with several builds in grant order, write-then-ack with progress the engine keeps, several writes per sink with per-document order, sink-decided backfill, continuity before trust, at-least-once requests, and item rejections separated from write errors. Each is guarded by a named test.

## The shape

```text
                 ┌─ lane ─▶ SinkEngine(primary) ─▶ write ×4 ─▶ ack ─┐
ChangeCapture ─▶ IngestEngine ─┤                                       ├─▶ Progress ─▶ confirm
  resolve · build once · publish└─ lane ─▶ SinkEngine(audit)   ─▶ write ×4 ─▶ ack ─┘
                 ◀─ request lane ─ Backfill { sink, indexes } ─────────────────────
```

One source, one stream, N sinks. The **ingest engine** (`libs/2-engine/src/ingest.rs`) owns the source side: capture, resolve, build, publish. One **sink engine** per sink (`sink_engine.rs`) owns delivery to that sink and that sink's seeding. The **stream** (`libs/1-ports/stream`) carries one lane per sink downward and a request lane upward. The engine's **progress** (`libs/2-engine/src/progress.rs`) records what was routed to each lane and has not landed; confirmation and fences are read off it. The **daemon** (`libs/3-daemon/src/supervise.rs`) stages every sink engine, then runs all engines as independent tasks. Everything an engine drives is a trait object, so backends swap without touching either loop.

## Documents are built once

The ingest engine buffers live changes per `BatchPolicy` (`[batch]` in `flusso.toml`; default 256 changes, 50 ms cap): it takes every change the stream has ready and commits the moment the stream would block, so a lone change on a quiet stream is built at once while a burst fills batches to `max_changes` (`1` reproduces a write per change). It resolves each to the `DocumentId`s it touches (an update whose pre- and post-image agree on every column a path reads resolves to nothing on that path; `source::relation_columns`/`root_columns` derive the columns, guarded by the `wal` e2e's `an_update_of_unread_columns_rebuilds_nothing` and the `pipeline` e2e's `an_update_of_an_unread_column_writes_nothing`), dedups them, and `build_many` assembles each touched document **once** even when several changes hit it and however many sinks there are. The result is published as one `Batch` of kernel `Envelope`s, tagged with the position of the last change, to every lane. A backfill (a *snapshot*) goes through the same build but is never resolved: it walks each requested index's root keys in pages (`DocumentBuilder::keys(index, after, limit)`, `engine::KEY_PAGE` = 1,024 at a time, the engine holding the last key read as the cursor), and each key is its own document of that index, built once (issue #385; resolving it like a live change cost a reverse query per related path and rebuilt related indexes' parents again and again). A page is read when the walk needs it, on the builder's pool, with no snapshot shared across pages (issue #386 stage 3): `prepare` made the slot before the first page, so a row that gets a key behind the walk reaches the live stream, and a page only names ids, each document read when it is built. The page future is kept in the snapshot, not in the `select!`, so a live change winning the `select!` drops no page half read. Guards: `tests::snapshot`'s `each_page_follows_the_last_key_the_walk_read`, the `keyset` e2e in `source-postgres` (every key type in key order, operators off the search path, a migration between pages) and the engine's `keyset_backfill` e2e (writes behind, ahead of and inside the page just read, a partitioned root, a stop mid-walk). They are published without a position and only to the lanes that requested them, ending with a `SnapshotComplete` marker. Both kinds interleave on one task, published in the order they were granted (below), so a document's later message is always its newer state. The sink engine keeps that order per document while it writes several items at once (below), so sinks need no versioning. Guards: `builds_a_repeatedly_touched_document_once_per_batch`, `batches_changes_into_a_single_build_and_flush`, `a_lone_change_on_a_quiet_stream_commits_without_waiting`, `max_delay_caps_a_batch_while_changes_keep_arriving`, `snapshots_go_only_to_the_requesting_lane`, `a_backfill_of_related_indexes_builds_each_document_once`, and the `backfill` e2e.

## At-least-once via write-then-ack and the progress

A position describes itself (ADR 0012): the source stamps each one as it emits the change, with how far it may confirm or fence while the change is the oldest outstanding (`confirm_before`, `fence_before`) and once it has landed (`confirm_through`), so the source keeps no map of what it emitted. The ingest engine **routes** a batch: it publishes it to every lane, then registers it in `Progress` with its oldest position, keyed by its last. A sink engine reports a lane item **landed** when its write returned with nothing refused for good, before it acks it, and how far its writes are searchable. From that `Progress` gives a `Landed` case: `Before(o)` while `o` is the oldest position some lane hasn't landed, `Through(p)` with nothing outstanding and `p` the newest routed, `Idle` before anything is routed. The ingest engine hands it to `ChangeCapture::confirm` after each commit when it changed, and on a one-second tick **always**, since the source's answer moves with idle WAL while the case stays put. The source decides the rest: `Through(p)` follows its horizon only while `p` is the last change it emitted (an emitted change not yet routed is in no lane), and `Idle` only while it emitted nothing; otherwise it stops at `p`'s own commit, or does not move. So the slot advances past a change exactly when **every** sink has made its documents durable, and never into the record of a commit not yet landed. The ingest engine writes only what it registers and `routed`; a sink engine only its lane's reports; neither takes the other's lock. A sink engine that dies before a write returns leaves the item unacked; its lane redelivers it to the restarted engine, and the rebuild is idempotent (deterministic ids, current state); a repeated landing report is harmless. Positions are monotonic for the life of the source, across reopened streams, so the `next_seq` test stays exact across an ingest restart. The status phase drops to `starting` while the ingest engine restarts and recovers when it follows the source again; only a clean end is `stopped`. Guards: `progress::tests` (`every_interleaving_answers_as_the_model_does`, `a_stalled_lane_pins_confirmation_and_its_own_fence_only`, `a_landing_reported_before_its_registration_still_counts`), `confirms_no_position_before_its_flush`, `redelivers_the_unacked_batch_to_a_restarted_sink_engine`, the channel adapter's `several_deliveries_can_be_outstanding_and_ack_independently`, the daemon's `failed_sink_engine_restarts_and_redelivers` and `failed_ingest_engine_restarts_and_resumes_the_stream`, the Postgres adapter's `ack::tests` (`a_change_emitted_but_not_routed_is_never_fenced_or_confirmed`, `the_tick_releases_idle_wal_while_routed_stays_put`, `a_fresh_process_never_confirms_its_first_unrouted_change`, `an_idle_stream_after_an_ingest_restart_still_releases_wal`, `a_reopened_stream_continues_the_numbering`).

## Several builds at once, published in order

The ingest engine runs up to `builds` `build_many` calls at once (`[concurrency] builds`, default 4; ADR 0012 stage 4, `ingest/builds.rs`), still from its one task. Once concurrent writes landed, the serial build was what bounded a backfill.

- **The gate.** Two batches can wait for a build slot: the live batch (once the stream would block or the batch closed) and the snapshot's (once full, or its walk is done). Live goes first, except every fourth grant both could take. The count moves only on such contested grants. A second live build starts only while the batch behind the first is full, so a trickle still batches itself, and a lone change on a quiet stream is granted the moment the stream would block.
- **Per document.** A batch is granted only when no running build holds one of its documents (64-bit id hashes, kept sorted per build; a collision only holds a batch back; nothing is hashed at `builds = 1`). So a later build of a document starts after the earlier one returned, and under Read Committed it reads newer state.
- **Grant order is lane order.** Every grant takes the next slot in a queue (at most `2 × builds` slots, running or built); the front is published once it is ready, so a lane gets items in grant order whatever finishes first. Live positions only grow along a lane and in `Progress`, which registers them in that order. A snapshot's `SnapshotComplete` takes a slot of its own, after its last batch.
- **Running a build.** A build is polled once where it is granted; one that doesn't finish then is spawned on its own task, so its decoding and scripts run beside the engine and it progresses while the engine publishes. Spawned builds are awaited through `Flights`. The live arm reads and resolves changes while builds run; it pauses only while the live batch is closed and waits for a slot.
- **Failure and stop.** A failed build, or a document failed under `stop`, stops every grant; the slots before it are published, nothing from it on, and the run awaits every running build before returning the error. A stop, and the end of the live stream, grant the buffered live batch once its documents are free, then finish and publish every build in order.

Guards: the engine's `ingest::tests` (`random_schedules_keep_every_document_in_order`, a seeded random schedule with failures and restarts that `FLUSSO_BUILD_SCHEDULE_SEED` replays; `builds_run_at_once_up_to_the_setting`; `a_document_is_never_built_twice_at_once`; `every_fourth_contested_grant_goes_to_the_backfill`; `a_failed_build_publishes_nothing_after_it`; `a_document_failed_under_stop_publishes_nothing_after_it_and_skip_goes_on`; `a_stop_finishes_the_builds_in_flight_and_starts_no_other`; `a_lone_change_on_a_quiet_stream_still_commits_at_once`; `one_build_at_a_time_builds_and_publishes_as_before`, recorded from the serial engine).

## Built documents within a byte budget

The ingest engine holds built documents within `[concurrency] max_built_mib` (default 512 MiB; ADR 0012 stage 5, `engine::Budget` in `libs/2-engine/src/budget.rs`), from their build until every lane acknowledged them.

- **Counted.** A build's documents are measured by a walk of their trees on the build's own task (`document_bytes`: strings, byte arrays, arrays, B-tree nodes; held to a counting allocator within 0.8–1.2 by `tests/heap_walk.rs`), at least 1 KiB a batch.
- **Reserved, then settled.** A grant reserves an estimate (the batch's ids × a running average per document of its kind) in `Builds::choose`; the build settles it to the measured size when it lands. A candidate the budget can't fit is simply not admissible: the gate's every-fourth counter doesn't move, and the loop waits for a release.
- **Released by the last copy.** The settled `Arc<Charge>` rides every lane's piece of the batch as `stream::Batch.hold`. The channel's ledger keeps a copy until the acknowledgement, so the bytes come back exactly when every lane acknowledged the piece and nothing can redeliver it. No lock: one atomic subtraction per drop.
- **Rules.** Total within the limit; backfill within half, so live keeps room; a kind holding nothing is always granted one batch, so a batch larger than the budget still builds, alone. Held stays within the limit plus the actual size of each batch in flight: a grant is checked against an estimate, then counts what it built.
- **Lanes.** `[stream] capacity` is deprecated: lanes built from configuration keep a backstop of 1,048,576 items, which the 1 KiB floor keeps from binding before the budget. With lanes that don't fill, `publish` doesn't block the loop; a stalled sink is felt as the budget filling, while the loop goes on landing builds and serving what has room.

Guards: `budget::tests`, `heap_walk`, and `ingest::tests`' `random_schedules_under_a_tiny_budget_stay_within_it_and_finish`, `a_stalled_sink_paces_builds_and_they_resume_when_it_does`, `live_keeps_room_beside_a_backfill_holding_its_half`, `a_batch_bigger_than_the_budget_still_builds`, `a_batch_redelivered_after_a_failed_write_gives_its_bytes_back_once_written`.

## Several writes per sink, one document at a time

A sink engine writes up to `writes` lane items at once (`[concurrency] writes`, default 4; ADR 0012 stage 2). Writing is the measured bottleneck: OpenSearch takes overlapping bulk requests about as well on one index as across several.

- **The window.** The engine takes an item from the lane only to use it: while a write slot is free, or, with only backfill waiting, to find a live item behind it, up to 32 waiting. A delivered item leaves the lane's bound, so each sink holds at most `writes + 32` delivered items beside the lane's `capacity`, about `writes` with live traffic alone. A granted write is started at once, so one that completes on its first poll is acknowledged in the same turn, as one write at a time was. With nothing waiting and no room to take more, the run waits only for a write landing, a control message or a position coming due, as one write at a time waited inside its flush: nothing can be taken from the lane, a stop changes only waiting backfill (there is none), and the engine isn't idle. One still running waits in `Flights` (`sink_engine/flights.rs`), which polls a write only when its own waker fired and never wakes the run by itself: `FuturesUnordered` woke its task after every pass that left all its futures pending, one empty wake-up for each write that had to wait, about 1 µs of CPU per lane item at one change per batch.
- **Admission.** An item starts only when no earlier unfinished item shares a document (`(index, id)`, hashed) with it. So a document is never written twice at once, and a later build lands after an earlier one: the per-document order the ingest engine's lane order gives.
- **Merging.** A write holds every item ready and admissible at once, of the kind the grant chose, across lanes and several of one lane, up to `[batch] max_changes` documents and the sink's `write_limit` (OpenSearch: `batch_size`), never splitting an item: `Sink::write_parts`. A live item that is ready while a write is out waits for it, at most `[batch] max_delay_ms` and never for a write already out that long, so both go out as one request (stage-7 §14; guards: `tests::wait`). A burst over several indexes goes out in writes of about a batch, not one per index. Each part is acknowledged, fenced and decided on its own: a `stop` rejection holds back and blames only its own lane. A lane behind a barrier, and an ordered sink, write one item alone. Rules: `docs/adr/0012-stage-notes/stage-7.md` §12; guards: `tests::merge`.
- **Selection.** Live items (they carry a position) go before backfill items, except every fourth grant both could take, which goes to the oldest admissible backfill item. A `SnapshotComplete` runs once everything before it on its lane is written: it seeds its index (`mark_seeded`) as a flight holding one write slot, and nothing after it on its lane starts until the seed returned. Other lanes keep writing and seeding meanwhile, so the seeds at the end of a backfill overlap each other and the writes still going. A seed that fails fails the run like a failed write. A reindex control message waits for the writes and seeds in flight.
- **Fences in position order.** *Applied* is reported to `Progress` per item when its write returns, before its acknowledgement. *Searchable* trails it in the same order, each position due by what its own write reported.
- **Caught up.** A write is caught up when nothing else is queued or waiting. A caught-up write makes every write that returned before it searchable (the `Sink::write` contract). Before the acknowledgement that leaves the engine idle, a position not yet searchable gets an empty caught-up write, so the last writes of a burst don't wait out `refresh_interval`.
- **Failure.** A failed write starts nothing new (a `stop` rejection, a write block or a missing target parks or restages its lane instead, see [Item-level rejections](#item-level-rejections-versus-write-wide-errors-and-parked-lanes)): the writes in flight are awaited and acknowledged when they succeeded, then the run ends with the error, and the lane redelivers only what is unacknowledged. The next run is a **barrier**, and so is the first run of a fresh engine (a previous process may have stopped on its first item): it writes the oldest item alone and opens the window only once a write landed, so a write that fails every time halts the sink as one write at a time did (nothing behind it lands, no run makes progress, the backoff grows, the lane fills). A fresh engine's oldest item is the oldest unconfirmed one: when that is an older batch already written (a sibling sink lags, or the confirmation never reached the source), it lands, the window opens, and disjoint batches past the rejected one, granted beside it or while it is in flight, can land before it fails. Nothing is lost. Guards: the engine's `after_a_failed_run_the_oldest_item_is_written_alone_until_it_lands`, the daemon's `a_stop_rejection_halts_its_lane_writing_several_items_at_once`.

Guards: the engine's `tests::concurrent` (`a_document_is_never_written_twice_at_once_and_its_versions_never_go_down`, a seeded random schedule that `FLUSSO_SCHEDULE_SEED` replays; `a_later_write_finishing_first_moves_neither_confirmation_nor_the_fence`; `live_goes_first_except_every_fourth_contested_grant`; `a_snapshot_complete_is_a_barrier`; `a_reindex_waits_for_the_writes_in_flight`; `tests::seeding`'s seeds at once, a failed seed, a stop and a reindex beside a seed; `a_failed_write_lets_the_others_finish_and_comes_back_alone`; `a_stop_finishes_the_writes_in_flight_and_skips_waiting_backfill`; `an_idle_engine_makes_its_last_writes_searchable`), `tests::busy`'s `a_busy_item_holds_back_only_the_items_sharing_its_documents`, and the OpenSearch sink's `concurrent_writes_each_send_their_own_documents` and `a_caught_up_write_refreshes_what_earlier_writes_left`.

## Backfill is each sink's decision

Staging (`SinkEngine::stage`) `ensure_index`es every mapping, asks the sink `is_seeded` per index, and sends one `Backfill { sink, indexes }` request up the request lane for the unseeded set. The indexes are staged concurrently, `STAGE_CONCURRENCY` (8) at a time, a fixed bound because OpenSearch applies index creations and alias changes one cluster-state update at a time, so more in flight gains nothing (4, 8 and 16 measured alike on a fresh cluster): each index's own steps stay in order, and nothing orders one index against another, since each has its own target. The `Sink` port says so: `ensure_index`, `is_seeded` and `reindex` may run at once for different indexes, never for the same one, and beside a `write`/`mark_seeded` of other indexes only (a lane staged again after its target went missing). Once an index fails no further index is started (a cluster that is down or never answers fails every index alike, and each further wave would cost another request timeout); the ones in flight finish, the error (`EngineError::Staging`) names every failure seen with its own error, and the daemon retries the whole stage, which starts the rest. A reindex control naming an index twice stages it once. The ingest engine walks the union of the requested indexes and publishes their documents to the requesting lanes only; a seeded sibling sees nothing, so a stateless sink beside OpenSearch no longer re-seeds it on every restart. `backfill = false` on a sink skips staging's request entirely and never marks anything seeded. Requests coalesce into one snapshot fanned to every requester: whatever is already queued is taken with no wait (every startup request is, since the daemon stages every sink before the ingest engine runs), and the engine holds for stragglers only while some lane has not asked, for at most the batch policy's `max_delay`, so a reindex fanned to every sink is one pass over the table and a single-sink backfill starts at once. Requests are at-least-once: the ingest engine acks a request only after its `SnapshotComplete` is published, so a crash mid-snapshot redelivers it; and a sink engine remembers which indexes it has requested and not yet seen complete, so re-staging after its own restart does not ask twice. Guards: `an_unseeded_sink_requests_a_snapshot_then_marks_seeded`, `a_seeded_sink_requests_nothing`, `backfill_false_makes_a_stateless_sink_live_only`, `concurrent_requests_for_the_same_index_coalesce_into_one_snapshot`, the daemon's `unseeded_sink_is_backfilled_without_touching_its_sibling`; for the concurrency, the engine's `tests::staging` (the bound, one index's steps in order and never overlapping, one request for the unseeded set, every failure seen named, no index started after a failure, a reindex naming an index twice) and the OpenSearch sink's `many_indexes_staged_at_once_each_get_their_own_generation` e2e (24 at once on a fresh cluster, where the first meta writes race to create `flusso_meta`, then a restart, then rebuilds).

## A seed is only as good as the stream behind it

Run order is `source.continuity()` → stage every sink → `source.prepare()` → serve requests and live. `continuity` is read-only (Postgres: does the slot exist?) and answers `Resumed` or `Fresh`; `prepare` creates the resume point and is the ingest engine's first act. On `Fresh`, every change since the last seed is unobservable, so each sink engine warns and stages `sink.reindex` plus `ensure_index` for every index still `is_seeded` (a fresh generation, so rows gone from the source drop on the swap, never an in-place reseed), and the normal backfill refills them.

The order is load-bearing twice. Rebuilds are staged **before** `prepare` creates the slot, so a crash in between comes back `Fresh` and re-stages instead of `Resumed` trusting stale seeds. `prepare` runs **before** any backfill page, so a write a page doesn't see is in the stream. The daemon enforces it by finishing every sink's first staging before it starts the ingest engine. Only seeded indexes are staged; an unseeded one is already being rebuilt and staging again would orphan a generation. Under `--skip-backfill` staging only warns. Guards: `fresh_source_rebuilds_seeded_indexes_before_prepare_then_snapshots`, `fresh_source_leaves_an_unseeded_index_to_the_normal_backfill`, `skip_backfill_with_a_fresh_source_stages_nothing`, the daemon's `fresh_source_rebuilds_seeded_sinks_before_preparing` and `every_index_of_every_sink_is_staged_before_the_source_prepares`, the sink's `deleted_generation_is_recreated_and_reported_unseeded` e2e, the Postgres `continuity` e2e, and the two `restart_*` cases in the engine's `pipeline` e2e.

## Reindex is an operation on one sink

A reindex reaches a running sink engine as a control message from the daemon (`DaemonControl::reindex(index, Option<sink>)`, behind `POST /reindex`). Once the writes in flight have returned, the engine stages a fresh generation (`reindex` + `ensure_index`, several indexes at once as at start) and sends a new `Backfill` request; the current generation keeps serving until the snapshot completes and `SnapshotComplete` lets the sink swap. Nothing restarts, and untargeted sinks are untouched; forcing every sink coalesces into one snapshot. A sink with `backfill = false` ignores it (nothing to rebuild), as does an index whose snapshot is still outstanding. The OpenSearch sink's own `reindex` also stages nothing for an index that is still unseeded, so a second reindex can't orphan the generation being built. Guards: `reindex_control_stages_and_requests_a_snapshot_without_restarting`, the daemon's `reindex_operation_targets_one_sink`.

## A stop is a drain

A stop is a drain, not an abort. The daemon hands the ingest engine an `engine::Stop`, which the engine checks between the live stream's items, never by cancelling a task: it reads nothing more, drops a snapshot in progress unacked (the sink asks again on the next start), publishes the batch it was building, waits with `drain_lanes` (the same drain that runs when the live stream ends) until every lane is acked, confirms what landed, and asks the source to close its stream once the position reached the server (`ChangeCapture::close_live`). A stalled sink holds the drain; the binary's deadline bounds it, and giving up is safe for the reason above. The user-facing sequence is [Stopping](../reference/cli.md#stopping). Guards: the engine's and the daemon's `tests::stop`.

## Item-level rejections versus write-wide errors, and parked lanes

`Sink::write` returns a `WriteReport`. `Err` is write-wide and stops **that sink engine** (once the writes in flight beside it returned), which the daemon restarts with exponential backoff (one second doubling to `max_restart_backoff`, default 60 s, and back to one second after a run that made progress: the sink engine's oldest unfinished lane item landed (a later item landing beside an older one that then fails is no progress), or the ingest engine moved its source forward, by its source reporting it read further than ever, keepalives on a quiet stream included (or, for a source that reports no such position, by confirming further than ever), or by finishing a backfill. Publishing alone is not progress: a restart publishes a replayed change or backfill page again) while the ingest engine and the other sinks keep running; its lane fills meanwhile, so with the in-process stream a stalled sink eventually paces ingest and pins WAL, and its per-sink lag and in-flight numbers are the alarm. An `Ok` report lists documents the destination applied the write but rejected individually, and, per index, the indexes it refused as a whole: `blocked` (a write block, an item-level `security_exception`) or `missing` (a generation deleted while running). `FailurePolicies` (a global default plus per-index overrides, resolved by logical name) decides each rejection when the write returns: `Skip` quarantines it (`Observer::on_document_quarantined`, with the sink) and acks the part so the poison isn't redelivered; `Stop` **parks the lane** (ADR 0012 stage 9). So does a blocked index, whatever the policy; a missing one is **staged again**.

A parked lane's parts go back in the sink engine's window unacknowledged, in receive order, so its marks, its fences and the slot stay where they are, and nothing of it is granted: it takes nothing more from its lane, and its items neither hold nor end a merge wait. When its backoff is due (1 s, doubling to `max_restart_backoff`, reset only when that lane's probe lands) its front item is written alone, a **probe**; landed, the lane opens and the rest follows; refused or blocked again, the backoff doubles. A stop probes every parked lane once more at once. A restaging lane, once nothing of it is in flight, runs `ensure_index` for its index alone beside the other lanes' writes (the port allows staging beside writes of other indexes), then `seeding` and a `Backfill` request when it is unseeded and none is outstanding, then opens and writes its items again; a failed staging is retried with the same backoff. The lane's state (`LaneHealth`: open, parked, restaging, with its backoff) lives on the `SinkEngine` and outlives a run, so a run that fails for another reason leaves a parked lane parked on its schedule; `stage` reopens a restaging lane, having ensured every index. Other lanes, and the merged write's other parts, land and are acknowledged as usual. The run ends only for a sink-wide failure: a write `Err`, a failed seed, a lane failing to deliver or acknowledge. The OpenSearch sink never retries a rejection, a block or a missing target inside a write. Guards: `tests::parking` (paused time: a refusal parks only its lane while the sibling lands and is fenced, probes and backoff, a lifted block opens the lane and a block quarantines nothing under either policy, a missing target restages one index, merged writes, `writes = 1` and an ordered sink, a stop's probe, a stop with a lane still blocked, parked across a failed run), `health::tests`, the `lane_parking` live e2e (a write block under `stop` and `skip`, a generation deleted mid-run), the sink's `bulk::tests` (`a_write_block_is_blocked_never_rejected`, `an_item_level_security_exception_is_blocked`, `a_flood_stage_block_is_busy_not_blocked`, `a_missing_alias_is_its_index_missing_not_a_failed_write`). An item refused as **busy** (429 or 503) is neither: the sink resends those items alone inside the same `write`, within `max_retries`, and fails the write when they are still refused, so the item stays unacked, and no later item sharing a document starts, until every document in it is written or rejected for what it holds. The retry lives in the sink because only it knows which items to resend and that the rest are already applied; the engine sees a slower write or an `Err`, as for a request-wide failure. A write keeps nothing between calls, so a failed one leaves nothing behind for the redelivered item to duplicate. Guards: `skip_policy_*`, `stop_policy_*`, `per_index_stop_*`, the sink's `items_refused_as_busy_are_resent_until_written`, and the engine's `a_batch_is_not_acked_until_its_busy_documents_are_written`.

## Observability is a trait

Both engines report lifecycle and progress to an `Observer` (`observer.rs`): sync, cheap, no-op by default, set with `with_observer`. Every sink-side event carries the `SinkName`; engine errors carry an `EngineId` (`Ingest` or `Sink(name)`). The daemon fans events to its per-sink `Status`; the binary attaches an OpenTelemetry observer. Guard: `reports_lifecycle_and_progress_to_the_observer`.

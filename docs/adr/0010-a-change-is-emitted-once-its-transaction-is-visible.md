# A change is emitted once its transaction is visible

flusso reads the database to turn a change into documents: reverse resolution finds the documents a row touches, and the build reads every row a document embeds. Those reads assumed the change's transaction was visible to them. It need not be (issue #343).

Postgres commits in three steps: it flushes the commit record, waits for synchronous standbys if `synchronous_commit` asks it to, and only then takes the transaction out of the proc array, which is when new snapshots see it. A logical walsender decodes up to the flushed WAL, so the change reaches flusso between the first step and the last. Every read flusso made in that window saw the state before the commit: a re-parented child resolved to its old parent only, an inserted child to none, and every document built then held the old rows. Nothing built those documents again, and the position was acknowledged, so a fence reported the stale document as applied.

On a quiet primary the window is microseconds, which a loaded CI runner stretches into flaky tests. Behind a synchronous standby it lasts the standby's round trip on **every** commit: with a standby emulated at 2 ms and 10 ms, 57–59 % and 98–100 % of lone changes ended up indexed with the value before their commit.

**Decision: the Postgres capture emits a transaction's changes only once a new snapshot sees the transaction.** Port and engine are unchanged; the guarantee is part of `ChangeCapture::live`'s contract ("a change is yielded only once it can be read back").

- The stream keeps the xid from each `Begin` and holds every committed transaction in `pending`, in commit order. The front one is emitted only once it is known readable.
- Snapshot reads (`SELECT pg_current_snapshot()::text`) run on a task of their own, one at a time, while a transaction awaits a check, so they overlap the engine's build and publish; the task lives as long as the stream and sleeps on a `Notify` otherwise, so a commit arriving as it goes idle always finds it (a task that exited on its own missed about one such commit in a thousand). The stream keeps the newest snapshot (up to a second old, so an xid is never widened against an old `xmax`) and checks each commit against it on arrival: a commit that was visible when it was taken needs no read of its own. A lone change costs one read, an idle stream none, and a stream running behind a burst few, since one snapshot covers every commit made before it. A read runs on its own one-connection pool, times out after 5 s, and is retried for 30 s before the stream ends with the error, so a pool timeout under load doesn't restart the ingest engine. The rule is `pg_visible_in_snapshot`'s, applied in Rust: below `xmin` visible, at or past `xmax` not, in between visible unless listed as running.
- **Widening.** pgoutput's xid has 32 bits; the snapshot's have 64. A decoded transaction is within 2^31 xids of the snapshot's `xmax`, so its full xid is `xmax` moved by the signed 32-bit distance between the two. `xmax` is the last finished xid + 1, **not** the next xid: the held transaction is usually at or past it. Treating `xmax` as the next xid, as the first prototype did, moved a held transaction one epoch back, below `xmin`, where it read as visible from epoch 1 on. A differential test checks the rule and the widening against Postgres's own function on literal snapshots at epochs 0 to 2.
- While the front transaction is held, the stream keeps reading up to a read-ahead bound (`max_changes × 16` changes), keeps handing confirmations to the replication client, and reads a snapshot every 0.5 ms for the first 20 ms (tokio's timer makes that about 1 ms), then backing off to 50 ms.
- A transaction that touches no table an index reads is not checked: nothing reads its rows. "Reads" means the tables the schemas name (`SourceSpec::all_tables`), so a table read only inside a `raw` filter's SQL isn't among them, and a transaction touching only that table is emitted unchecked. That is no new exposure: flusso never rebuilds a document on a change to such a table either.

## Considered options

- **Wait per batch in the engine** (a neutral `ChangeCapture` method, "await the source readable up to this position", called before a batch's first read). Measured as cheap. Rejected: resolution would move from buffering to the batch's commit, the port would gain a method every read path must remember to call (the failure mode `fence_before` already has), and the wait would block the ingest task, snapshots and backfill requests included.
- **Hold at the capture, one query per transaction, inline.** The same guarantee with a simpler loop. Measured 3.5–4.5× slower to drain a backlog and about a second behind a burst of 4,000 single-row transactions: the query sits between every two transactions. A query run inline also shrinks batches, because the stream isn't ready while it is in flight. Rejected for the coalesced form on its own task.
- **Check only the batch's newest transaction.** Wrong: transactions leave the proc array in no fixed order (the synchronous-replication wake-up releases waiters together, and each then ends its own transaction), so a newer one can be visible while an older one is not. Every held xid is checked; a test releases the later of two held commits first.
- **`pg_xact_status(xid8)`.** It reports `in progress` until the proc array lets go (it checks the proc array before the commit log), so it would work too, but one xid at a time.
- **Read under a snapshot known to include the commit.** Postgres offers no way to wait for a snapshot covering an LSN or an xid. An exported snapshot belongs to slot creation, not to each commit.
- **Rebuild when the row read disagrees with the WAL's post-image.** Only updates carry a post-image (inserts, partitioned tables and tables without a full identity do not), and a match on one row says nothing about the other rows a document embeds. Rejected.
- **Delay every read by a fixed time.** Not a guarantee under any standby. The tests hold a commit 8 s with nothing written and require the document within 1 s of the release, so a delay fails them either way.

## Consequences

- **One held transaction stalls the whole stream.** Commit order is kept, so every later change, from every session, waits behind it. What makes a commit wait: a synchronous standby that is down or slow under `synchronous_commit = on`/`remote_write`/`remote_apply`, `remote_apply` with a standby's `recovery_min_apply_delay`, or one session that sets `synchronous_commit` itself.
- **A transaction that never becomes visible stalls indexing**, where 0.17 indexed it stale. No opt-out. After 5 s the stream warns, naming the sessions waiting on synchronous replication (`pg_stat_activity`, `wait_event = 'SyncRep'`), and repeats every minute; `/status` (`visibility_wait_seconds`) and the `flusso.replication.visibility_wait` gauge report the wait. The operator brings the standby back or takes it out of `synchronous_standby_names`. The wait is timed from when that transaction was first found invisible: the clock records the xid it times and outlives a stream, so an ingest engine restarted every few seconds keeps counting (and warns) instead of starting over; it is cleared once the transaction is emitted, and when the capture refuses the server. The stall inspection is best effort and bounded: one that fails or takes longer than 5 s is reported in the warning, and the hold goes on.
- **flusso refuses to be the synchronous standby of the server it reads.** A commit would wait for flusso to confirm it while flusso waits for the commit to become visible: a deadlock. At start (before anything writes, and again before each stream opens) the capture refuses when `synchronous_standby_names` takes in its `application_name`, by name or by `*` in any form, and `flusso check` fails on the same check. `*` is refused even where real standbys could fill the quorum: flusso counts among the candidates. The message names a remedy that works for the form: a name can be taken out or flusso renamed, while `*` matches any name, so only replacing it with the standbys' names helps. Its walsender's row in `pg_stat_replication` exists only once the stream is open, and reads `async` until the first feedback, so it can't be checked at start; when a hold passes 5 s the stream reads both the setting and that row, and stops with the same message. The setting alone decides it for any role; the row is a cross-check, readable only with `pg_read_all_stats` (any other role sees just its walsender's `pid`, checked on PostgreSQL 16). The ingest engine's restarts then keep refusing at start. A deployment that ran on 0.17 under such a setting (each commit waited on flusso's stale confirmation) does not start on 0.18.
- **The check and the reads need the primary the stream reads.** Visibility on a standby follows its replay, not the primary's proc array. The capture refuses a server in recovery, on its SQL and on its replication connection. That also refuses logical decoding from a standby (PostgreSQL 16+), which flusso never tested; the connection URL must reach the primary, not a pooler that routes reads to replicas.
- **Fences stay honest only while the hold lives in `pending`.** Nothing in `pending` is registered, and the horizon never moves past buffered changes (a keepalive or a filtered commit is ignored while `pending` is not empty), so neither confirmation nor a fence can pass a held commit. Holding a transaction anywhere else needs both guards extended.
- **A lone change costs one more round trip** (a few hundred microseconds on a local Postgres; within the noise of the scenario harness's visible latency). **A burst costs a few reads**: a stream running behind the writers meets mostly commits an earlier snapshot already covers (12 to 59 reads for 10,000 changes, counted in a scratch build). Burst batches are cut by the engine's `max_delay`, not by the stream: of about 100 batches per burst, the stream was not ready for 0 to 3 on either side, so a hold doesn't shrink batches the way a read per check did. Over 8 alternating release rounds of the `reference` scenario (load average 7 to 32, a shared machine) the branch's drain was ×0.80 to ×1.40 of `main`'s, a median ×1.20 and lower in 3 of 8: no slowdown shows, and the machine was too loaded to rule out a small one. **Behind a synchronous standby** (the `sync-standby` scenario, 2 ms) the visible latency p50 stayed at about 29 ms; `main` there never indexed some probes' committed values at all.
- **`pg_current_snapshot()` needs PostgreSQL 13 and no privilege**: it ran as a plain `LOGIN` role. flusso requires 14.
- **PostgreSQL 17's `synchronized_standby_slots`** narrows the window (the walsender waits for the listed standbys) but does not close it: the commit's session still has to finish after the standby answers.
